# 思源任务块识别与映射（文档任务块 ⇄ CalDAV VTODO）

> 对应 GitHub issue #2。本文件是功能说明 + 实现方案 + 界面改动的总文档，供核对是否遗漏。
> 提交：`c5b485c feat: 文档任务块 ⇄ VTODO 识别与映射（issue #2）`（**尚未发版**）。

---

## 1. 功能概述

把思源文档里用原生语法写的任务块：

```markdown
- [ ] 待办1
- [x] 已完成的待办
```

自动同步成 CalDAV VTODO（待办），可在手机端（Tasks.org / DAVx⁵ 等）管理：

- **文档里打勾** → 服务端 VTODO 标完成；
- **手机端标完成** → 思源里的块勾选态跟着打上；
- **文档里的块被删除** → 对应的 VTODO 一并删除；
- **在插件里删除该 VTODO** → 思源里的块也一并删除。

识别与映射分两种入口：

1. **批量扫描**：在「扫描时机」选定的触发点扫一遍（范围可配），也支持设置页「立即扫描」、块菜单里的「扫描任务块（当前文档）/（全部）」。
   - ⚠️ **自动同步定时器（默认每 15 分钟）只跑 `syncAll()`，不扫任务块** —— 这是早期文档的偏差，已更正。任务块只在以下时机被扫：
     - 插件启动后约 3 秒（受 `blockSyncOnStartup` 开关）；
     - 手动点「同步」（受 `blockSyncOnManualSync` 开关）；
     - 关闭当前文档（受 `blockSyncOnDocClose` 开关，只扫刚关掉的那个文档）；
     - 设置页「立即扫描」按钮、块菜单「扫描任务块」项（用户主动触发，**不受上面三个开关限制**）。
   - 扫描默认走**增量**（只查改动过的任务块），详见 2.5。
2. **单笔转换**：在思源里右键某个任务块，用块菜单手动同步或取消同步（见第 6 节）。

## 2. 实现方案

### 2.1 身份锚点：Block ID（不是文本匹配）

每条由任务块转来的 VTODO，在其 ICS 里写入一个自定义属性：

```
X-SIYUAN-BLOCK-ID: 20261028123456-abcdef
```

- 该属性被纳入 ICS 的 `MANAGED` 属性集，**手工编辑/服务端回写时不会丢，也不会重复拼一次**（`src/core/ics.ts`）。
- 映射关系以 Block ID 为准，**改文字、改标题、甚至插件配置清空后都能靠服务端这份属性重建映射**，不会因为文字对不上就失联。
- 这是与编辑器里「手工新建待办」的唯一物理区别：编辑器建的 VTODO 没有 `X-SIYUAN-BLOCK-ID`，不会被当成本地任务块。

### 2.2 三方对账

每轮扫描跑一次对账，对比三方状态：

| 来源 | 内容 |
| --- | --- |
| ① 文档侧 | 内核 SQL 扫出来的任务块（id / 文字 / 勾选态） |
| ② 服务端侧 | 同步拉回的 VTODO（含 `X-SIYUAN-BLOCK-ID`） |
| ③ 本地 store | 已建立的映射（`CalItem.blockId` + 缓存的 `blockText`/`blockChecked`） |

产出四类动作：

- **create**：块有、映射无、服务端也无 → 新建 VTODO。
- **push**：块侧改了（文字/勾选）→ 推服务端。
- **writeback**：服务端完成态变了 → 回写块的勾选态。
- **delete**：块没了（按 ID 直接查在不在，不受扫描范围影响）→ 删 VTODO。

> ⚠️ **删除判生死按 Block ID 直接查存在性**，不靠扫描范围。
> 这样「文档被删且当时没打开」「笔记本被删」都能正确跟删 VTODO；
> 反过来，块只是「不在本次扫描范围内」（文档关着、不在指定笔记本）**绝不能误删**。

### 2.3 状态映射与冲突

| 方向 | 规则 |
| --- | --- |
| 块 → VTODO | `checked` → `COMPLETED/percent=100`，否则 `NEEDS-ACTION/percent=0` |
| VTODO → 块 | `COMPLETED` → 块打勾 `- [X]`；**`NEEDS-ACTION` 一律不回写块**（见 2.7） |
| 文字 | **一律以块为准**（详见 2.4） |
| 完成优先 | 两边都动了、其中一边是完成 → 按完成处理（完成是终态，不会来回翻转） |

待办块没有「放弃」状态，对应到 VTODO 只有「完成 / 未完成」两态（按完成映射）。

### 2.7 完成态回写是**单向**的：只许勾上，不许取消（2026-10-30 用户实测踩中）

**规则**：服务端完成态**只允许**「勾上」块，**绝不允许**「取消勾选」块。

```
服务端说「已完成」+ 块说「没完成」 → 回写块（勾上）✓
服务端说「未完成」+ 块说「已完成」 → 以块为准 + 推送服务端，**不回写块** ✓
```

**为什么不能信服务端说「未完成」**：服务端那份完成态**可能因为同步冲突而与本地不一致**。
⚠️ **不要归咎于「Baikal 会降级完成态」** —— 那是错的，2026-10-30 实测证伪：

- Baikal **完整保留** `STATUS:COMPLETED`：新建即 `COMPLETED` → `GET` 仍是 `COMPLETED`；
  改回 `COMPLETED` → `GET` 仍是 `COMPLETED`；等 3 秒后再 `GET` → 仍是 `COMPLETED`。
- 服务端上 199 条 `COMPLETED` 的条目，**逐条 `GET` 与插件实际用的 `REPORT` 两条路径**
  读回来的状态分布完全一致（199 `COMPLETED` / 5 `NEEDS-ACTION`）。
- 曾经被当作「降级活证据」的 8 条「本地 `COMPLETED` / `raw` 里 `STATUS:NEEDS-ACTION`」是**假象**：
  `raw` 是**本地缓存的旧原文**（上传成功后也不刷新，见 `sync.ts` 的 `item.raw = item.raw || ics`），
  不是服务端当前内容。逐条 `GET` 服务端 → 那 8 条**全是 `COMPLETED`**，etag 也与本地一致。

**真正的事故机制是 `If-Match` 冲突**：插件更新条目时带 `If-Match: <本地 etag>`（乐观锁）。
若服务端内容已被别的客户端改过 → 服务端返 **412** → 插件按账户冲突策略
（`server` = 服务端优先）**丢弃本地改动**，本地完成态被服务端那一刻的状态覆盖。
若那一刻服务端是 `NEEDS-ACTION`，块来源条目的完成态就被污染 → 下一轮对账判定
「服务端未完成」→ 回写文档 → 把用户已勾好的 `- [X]` 拍成 `- [ ]`。

而**块是用户的主数据**，服务端条目是从块派生出去的影子 —— 用影子去取消主数据的勾选，
方向就反了。

**踩坑经过**：用户「AI开发」文档里 29 个（连同其它文档共 60 个）已勾选的任务块，
在 16:20:06~16:20:13 与 16:30:28~16:30:39 两段秒级连续的批量回写里被全部拍成 `- [ ]`。
根因链：条目完成态被 412 冲突覆盖成 `NEEDS-ACTION` → 缓存记着「块是勾选的」→ 判定落进
`serverChanged` 分支 → `nextChecked = serverCompleted = false` → 回写块取消勾选。
修复后同一场景：**回写 0 次**，且把服务端纠正回 `COMPLETED`（自愈）。

**三重保险**：
1. 判定层：`serverChanged` 分支改为「服务端勾了才回写勾上；服务端没勾 → 以块为准」。
2. 结构性保险：`writebacks` 里**永不允许出现「把已勾选的块改成未勾选」**的条目 ——
   哪怕将来判定逻辑又被改错，最坏也只是「该勾的没勾」，绝不会动用户的主数据。
3. 漂移检测只认「服务端完成、块未完成」这一个方向 —— 否则服务端不支持完成态时，
   每轮扫描都会把所有条目按 ID 捞回来重新对账（白跑一轮）。
4. `mergeServerItems`：块来源条目的完成态**自我保护** —— 本地记着「已完成」而服务端说
   「未完成」时保留本地态，避免冲突污染扩散到插件各处（待办列表显示错乱、反复推送）。

> 代价：在别的客户端**取消**勾选，不再同步回文档。取消勾选只能由用户在文档里亲手做。
> 这是有意取舍：用户的主数据在文档里，服务端那份可能因 412 冲突与本地不一致。

### 2.4 为什么不回写块文字（重要设计取舍）

块的 `content` 是纯文本，但块里可能有**加粗、行内代码、引用 `((id "文本"))`、图片**等富文本。
若用纯文本 `updateBlock` 回写，会把富文本一律拍平、毁掉格式。

因此约定：**文字永远跟随块**，服务端标题只是块的镜像。

- 块改了文字 → 推服务端（服务端被别的客户端改的标题，下一轮会被块覆盖回来）；
- 服务端改了文字 → **不**回写块（避免毁格式）。
- 需要「手机端也能改名并写回文档」的诉求，需另行评估（得改成 DOM 级增量改写），本期不做。

### 2.5 增量扫描（2026-10-30）

**问题**：原来每轮扫描都是**全量** —— `SELECT … FROM blocks WHERE type='i' AND subtype='t' … LIMIT 5000`，
把库里**所有**任务块的 `content` + `markdown` 拉回来。任务块一多（几千个），每轮都要传几百 KB~几 MB，
而且 `LIMIT 5000` 一旦触顶就会**静默漏掉**后面的块。

**可行**：思源内核 `blocks` 表有 `updated` 字段（本机实测：`YYYYMMDDHHmmss` 字符串，本地时间、**秒级**、
**逐块**更新 —— 一篇文档里 33 个任务块就有 33 个不同的 `updated` 值）。等宽数字 → 字典序可比，
于是可以直接按它做增量：

```sql
SELECT id, content, markdown, root_id, box, hpath FROM blocks
WHERE type = 'i' AND subtype = 't'
  AND (updated > '20261030095629' OR updated IS NULL OR updated = '')
  AND id NOT IN (SELECT block_id FROM attributes WHERE name = 'custom-caldav-skip')
LIMIT 5000
```

> ⚠️ `OR updated IS NULL OR updated = ''` 这半句是**兜底**：老数据 / 导入来的块没有时间戳，
> 而空串跟任何非空串比较都更小 → 没有兜底，这些块**永远扫不到**（静默漏同步）。

**但光有增量不够** —— 全量扫描还承担两个「**非块侧变化**」的职责，增量看不见：

| 职责 | 全量扫描怎么做 | 增量模式下怎么做 |
| --- | --- | --- |
| 服务端改了、块没动（手机端勾完成 / 改标题）→ 回写块 | 每轮都扫到该块，顺手对账 | **漂移检测**：拿「服务器态 vs 缓存的块态」比对（`blockItemDrift`），把有漂移的条目按 ID **捞回块**再对账（`scanTaskBlocksByIds`） |
| 块被删了 → 删 VTODO | 扫不到 → 查存在性 | 同左（删掉的块没有 `updated`，只能靠**按 ID 查存在性**判定） |

> 漂移检测能成立的前提是**对账缓存（`blockText`/`blockChecked`）不被服务端拉取抹掉**。
> 原先 `mergeServerItems` 是整体替换条目，服务端回来的 ICS 里没有这两个字段 → 缓存被清空 →
> 对账判不出「块改了还是服务端改了」，只能「以块为准」，于是**手机端勾完成会被块的状态盖回去**。
> 现已在 `mergeServerItems` 里沿用本地那份缓存（`blockId` 一并沿用，防映射断链）。

**水位线**（`blockScanWatermark`，epoch 毫秒，随数据落盘）与三重保险：

| 情形 | 行为 |
| --- | --- |
| 有水位线且一切正常 | **增量**：只查 `updated` 晚于水位线的块；水位线**回退 2 秒**（`updated` 只到秒，防同秒改动漏掉） |
| 从没扫过 / 用户手动「扫描全部」/「立即扫描」 | **全量** |
| 扫描范围变了（换范围模式、增删笔记本） | 水位线作废 → **全量**（旧水位线不覆盖新范围） |
| 距上次全量超过 **24 小时** | 强制**全量校准**（兜住属性变更、导入、数据库重建等不会体现在 `updated` 上的改动） |
| 范围是「打开的文档」或「仅日记」 | **一律全量**、且**不推进水位线** —— 这两种范围的成员会随时增减（文档会关掉、文档会被设成日记），水位线的含义是「水位线之前的改动我全看过了」，成员会变时这个前提不成立 |
| 扫描限定某个文档（关文档时 / 「扫描当前文档」） | 该文档**全量**扫；**绝不推进全局水位线**（它没覆盖全库） |
| 扫描结果被内核截断 | **不推进水位线**（没扫全，推了就永久漏块） |

设置项 `blockSyncIncremental`（默认开）可关掉，退回「每次全量」。

**顺带修掉一个会删数据的坑**：思源内核 `/api/query/sql` **没写 `LIMIT` 时只回 64 行**
（响应里 `limit:64, truncated:true`），超出的行**静默丢弃**。原先的存在性判断
（`SELECT id FROM blocks WHERE id IN (…)`）没写 LIMIT → 映射超过 64 条时，第 65 条起会被判成
「块没了」→ **误删用户的待办**。现所有查询都显式写 LIMIT，并检查 `truncated` 标记。

### 2.6 删除判生死：唯一依据是「块还在不在」（2026-10-30 用户实测踩中）

> **用户实测现象**：「刷新」得到 100+ 条块来源 VTODO → 编辑其中一篇文档删掉几个任务块 →
> **关闭该文档** → 触发单文档扫描 → 结果**其它文档的 100 多条 VTODO 全被删了**，
> 只剩本文档剩下的 2 条。

**根因**：单文档扫描（`docIds` 收口）时，代码把「存在性查询」也按文档收口了 ——
只把**本文档**的块查出来当「免删白名单」。而白名单 `existing` 的语义是
「**这些块还活着，别删**」：别的文档的块没被扫到，**只是因为本轮范围窄**，
不是「块没了」。把它们排除在白名单外 → 判成孤儿 → **全部进删除队列**。

> **教训**：我把「收窄删除范围」的意图，实现成了「收窄免删范围」，**语义正好反了**。

**铁律三条**（改动这块前必读）：

1. **判生死只有一个依据：这个块在数据库里还在不在**（按 ID 查存在性）。
   扫描范围只决定「哪些块进入本轮对账」，**不决定「谁该死」**。
2. **存在性查询必须覆盖全部 `missing` 块**，绝不能按 `docIds` / `scope` 过滤。
3. **存在性查询失败 ≠ 块没了**。内核报错（`code != 0`）或网络异常时返回 0 行，
   若当成「全都查到了没有」→ 全库映射被判成孤儿 → 一次性删光。
   现 `blocksExistById` 返回 `{ found, failed, truncated }`，
   `failed`/`truncated` 时**本轮一个都不删**（宁可留着旧的，也别删用户的）。

**双重保险**：删除条件是「**在白名单外**」**且**「**本轮确实查过存在性**」（`checked` 集合）。
这样即使将来谁把白名单算错，最坏结果是「该删的没删」，绝不会「不该删的删了」。

## 4. 配置清单

「设置 → 思源任务块识别与映射」区域，受**总开关** `blockSyncEnabled`（默认关）控制；关闭＝完全停用（不扫描、无块菜单、不同步、「立即扫描」只提示未启用）。

| 配置项（key） | 界面文案 | 取值 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `blockSyncEnabled` | 启用文档任务块识别与映射 | 开关 | 关 | 总开关，关则全功能停用 |
| `blockSyncCalendarUrl` | 文档任务块转 VTODO 的默认日历 | 空 / 某日历 | 空 | 空＝复用「新建条目的默认日历」及其回退链 |
| `blockSyncDefaultEnd` | 默认结束时间 | `sameAsTodo` / `none` | `sameAsTodo` | `sameAsTodo`＝跟随「新建待办任务时默认结束时间」；`none`＝无日期任务（不写 DUE） |
| `blockSyncScope` | 自动扫描范围 | `open` / `daily` / `notebooks` / `all` | `all` | 打开的文档 / 仅日记 / 笔记本 / 全部文档 |
| `blockSyncNotebooks` | 指定笔记本（范围=笔记本时多选） | string[] | `[]` | 范围选「笔记本」才出现，列出本工作区全部笔记本多选 |
| `blockSyncMarks` | 标记 | `["badge"]` / `["prefix"]` / 两者组合 | `["badge"]` | 加「文档」小角标（纯 UI）/ 自定义前缀（写进标题） |
| `blockSyncPrefix` | 自定义前缀文本 | 任意串 | `[文档]` | `blockSyncMarks` 含 `prefix` 时写入 VTODO 标题，形如 `[文档]待办1` |
| `blockSyncOnStartup` | 扫描时机：插件启动后（约 3 秒）自动扫 | 开关 | 开 | 非手动路径；与 `blockSyncOnManualSync` 互不重叠 |
| `blockSyncOnManualSync` | 扫描时机：手动点「同步」时自动扫 | 开关 | 开 | 「立即扫描」按钮与块菜单单笔不受此项限制 |
| `blockSyncOnDocClose` | 扫描时机：关闭当前文档时扫该文档 | 开关 | 关 | 保守默认；受总开关 gate，只扫刚关闭的那篇文档（捕获其改动 / 删除） |
| `blockSyncIncremental` | 扫描方式：增量扫描（只查改动过的任务块） | 开关 | 开 | 关掉则每次全量扫描（见 2.5） |

> 基准时间口径与编辑器一致：开始＝今天下一个整点，结束＝开始 +（1h 或 8h，依 `todoDefaultEnd`），全天待办沿用「次日」兜底。
>
> ⚠️ **「扫描时机」三个开关只 gate 自动/半自动扫描**，不 gate 用户主动触发的行为（「立即扫描」按钮、块菜单三个单笔项、块菜单两个「扫描任务块」固定项）。

## 5. 界面改动

### 5.1 设置页卡片（手风琴 + 胶囊开关）

「思源任务块识别与映射」区域做成**与「日历账户」单张卡片同款的手风琴**：

- **头部**是「启用文档任务块识别与映射」**胶囊式滑动开关**（`b3-switch`，绿色滑动胶囊，不再是打勾 checkbox）。开启＝展开下方全部子设置；关闭＝收起且完全停用（不扫描、无块菜单、不同步）。点头部或点头部的开关都能切换。
- 展开后有：扫描时机（三个独立开关）、默认日历、默认结束时间、扫描范围（选「笔记本」展开多选列表）、标记（角标 / 前缀，勾前缀出现输入框）、以及两个动作按钮。

> 设计依据：用户要求「全局开关打开时下面才展开、否则隐藏」，且开关样式要像账户卡片那张绿色胶囊。故复用 `.caldav-acc` 手风琴结构 + 思源原生 `b3-switch`。

- **立即扫描**：当场扫一遍（不等同步周期），结果显示在右侧提示区。
- **一键清理**：删掉全部由任务块转来的 VTODO（**文档里的块不动**），**二次点击确认**（5 秒窗口内再点一次才执行，不用 `confirm()`），结果回显。
  - ⚠️ 若开关仍开着、范围仍覆盖着，下一轮同步会重新建回来 —— 后悔了用它清空，顺手关开关即可。

### 5.2 任务视图 / 侧栏角标

来自文档任务块的待办，在标题前加一个「**文档**」小角标（`[文档]` 文字或文档图标，取决于视图），提示它源自思源任务块、双向联动。可在设置里关掉（纯 UI，不动数据）。

### 5.3 单笔映射菜单（重点 · 双入口）

单笔转换现在有**两个入口**，功能完全一致（同一套三态同步项，共用 `buildBlockSyncMenuItems`）：

**入口 A — 右键正文（open-menu-content）**
在思源文档里对**某个任务列表块的正文文字**右键 → 原生块右键菜单里。
- 由 `eventBus.on("open-menu-content", …)` 钩子注入（`src/index.ts` 的 `onBlockMenu()`）。
- ⚠️ 思源内核（v2.9.4+）会把所有插件注入项**自动收进一个名为「插件」的子菜单**（带拼图图标），本插件无法改这个名字（核心写死）。三态同步项平铺在这个「插件」子菜单里。

**入口 B — 点块左侧图标把手（click-blockicon）**
点任务块左侧的 `⋮⋮` 图标把手 → 弹出的块菜单里。
- 由 `eventBus.on("click-blockicon", …)` 钩子注入（`src/index.ts` 的 `onBlockIconMenu()`）。
- 该路径下插件**完全掌控 label**，故用一个名为 **「任务块 ⇄ VTODO」** 的子菜单收拢同步项（⇄ 为普通 Unicode 箭头，渲染正常），不再受「插件」分组命名限制。

> 两个入口**都需先打开总开关**，否则菜单不出现；都对非任务块（标题/段落/图片）自动不注入。

- 菜单顶部固定挂**两个「扫描任务块」固定项**（无论该块是否已映射都出现，属用户主动触发）：
  - **扫描任务块（当前文档）**：从右键的块反推出它所属的文档，只扫那篇文档。
  - **扫描任务块（全部）**：按「扫描范围」设置扫全部（与「立即扫描」同语义）。
  - 这两项**始终出现**，且不受 `blockSyncOnStartup` / `blockSyncOnManualSync` / `blockSyncOnDocClose` 三个开关限制。

- 菜单项**三态**（位于两个固定扫描项之后），取决于该块当前状态：

| 块状态 | 菜单项 | 行为 |
| --- | --- | --- |
| 未同步 | 「同步此任务到 CalDAV」 | 单笔建 VTODO，写 `X-SIYUAN-BLOCK-ID` 锚定 |
| 已同步 | 「取消同步（删除对应的 CalDAV 待办）」 | 删 VTODO + 给块打 `custom-caldav-skip` 忽略标记（**见 5.4**） |
| 已忽略 | 「重新同步到 CalDAV」 | 清标记 → 立刻重建 VTODO |

> 菜单钩子全程 try/catch，插件异常不会污染思源右键菜单体验。两入口注入路径均为**同步** `addItem`，杜绝此前「`await` 把菜单项推迟到渲染之后而丢失」的 bug。

### 5.4 「取消同步」为什么必须打忽略标记

只删 VTODO 而不标记，下一轮扫描会把它当成陌生块**再建一个**（正是实现中堵掉的洞）。
忽略标记 `custom-caldav-skip` 打在**块自身属性**上（不是配置里），所以配置清空 / 插件重装后标记还在，不会被扫回来。

## 6. 删除语义（双向）

| 操作 | 结果 |
| --- | --- |
| 文档里删除任务块 | 按 ID 查到块已不存在 → 删对应 VTODO |
| 在插件 UI 删除该 VTODO | 删除块（`updateBlock` 删除块节点） |
| 删文档 / 删笔记本（当时没打开） | 按 ID 查存在性 → 块已不在 → 跟删 VTODO |
| 块菜单「取消同步」 | 删 VTODO + 打 `custom-caldav-skip`（不删块，且不再被扫描重建） |
| 设置「一键清理」 | 删全部块来源 VTODO（**不删块**），下轮若开关+范围仍覆盖会重建 |

## 7. 已知限制 / 待你核对的点

1. **手机端改标题不回写文档**（2.4 取舍）：文字以块为准。若你希望「手机端改名也写回文档」，需评估 DOM 级增量改写，本期未做。
2. **文字冲突策略预留未启用**：`planBlockSync` 有 `conflict` 入参（local/server），但目前文字一律以块为准，`conflict` 仅占位（`void conflict`）。后续若开放「服务端优先」再接上。
3. **引用 / 富文本块**：扫描以 `content`（纯文本）为准；引用 `((id "文本"))` 在块文字里已还原为纯文本，转 VTODO 标题时不含链接。
4. **删除判生死只在「块确实从数据库消失」时才删**（见 2.6）。**任何情况下查不实都宁可不删** —— 误删待办的代价远大于多留一条。
5. **扫描上限**：内核 SQL 显式 `LIMIT 5000`，超大量的库可能被截断（本机实测任务块 105 个，远低于上限）。**已缓解**：增量模式下返回的只有改动过的块；且内核的 `truncated` 标记会被检查 —— 截断时**不推进水位线**并报错，不会静默漏块。
5. **「打开的文档」范围**：若当前没有任何文档打开，扫描结果为空（**不会退化成全库**）。
6. **Obsidian 端**：本期只改思源端；Obsidian 没有「块」概念，本次不涉及（Obsidian 仓全量测试仍绿）。
7. **服务端完成态可能因同步冲突而与本地不一致**：实测 Baikal **不会**无缘无故降级 `COMPLETED`（2026-10-30 四轮往返 + REPORT/GET 双路径核对，见 2.7）。但插件更新时带 `If-Match`，服务端内容已变会返 **412**，按「服务端优先」丢弃本地改动 → 完成态被覆盖。插件已按 2.7 处理（以块为准 + 推送纠正 + 绝不反向取消勾选），**块不受影响**。
